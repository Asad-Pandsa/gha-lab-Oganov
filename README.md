# Ответы на вопросы 
# вопросы
1. Из каких элементов состоит workflow и как они вложены друг в друга?
2. Чем job отличается от step?
3. Чем запуск по push отличается от запуска кнопкой (workflow_dispatch)?
4. Как безопасно передать в workflow пароль или токен?
5. Что такое артефакт и зачем он нужен?
6. Как заставить один job дождаться завершения другого? Зачем нужен линтер, если есть
тесты?
# Ответы 

1. Workflow — это верхнеуровневый процесс автоматизации, описываемый в YAML-файле. Он содержит триггеры событий, глобальные переменные и список задач. Внутри каждой задачи определяются параметры виртуальной машины и последовательность шагов. Шаги в свою очередь, состоят из консольных команд или готовых модулей
2. job выполняется на отдельной чистой виртуальной машине и по умолчанию запускается параллельно с другими задачами. Step — это отдельная команда или готовое действие внутри одной задачи, которое выполняется строго последовательно с другими шагами этой же задачи на той же самой виртуальной машине.
3. Запуск по событию push происходит автоматически при отправке изменений или новых коммитов в репозиторий. Запуск по событию workflow_dispatch выполняется вручную пользователем через веб-интерфейс GitHub (кнопка Run workflow) или через API.
4. Секретные данные нужно сохранить в настройках репозитория в разделе Secrets (Settings → Secrets and variables → Actions). В коде workflow к ним обращаются через контекст ${{ secrets.ИМЯ_СЕКРЕТА }}. GitHub Actions автоматически скрывает эти значения и заменяет их на звёздочки в логах выполнения.
5. Артефакт — это файл или папка, созданная во время работы workflow и сохранённая на серверах GitHub. Он нужен для передачи файлов между изолированными задачами, а также для того, чтобы разработчик мог скачать готовые результаты работы конвейера себе на компьютер.
6. Для этого в описании зависимости задачи нужно указать ключевое слово needs: с именем задачи, завершения которой требуется дождаться. Линтер выполняет статический анализ исходного кода без его запуска, быстро находя синтаксические ошибки, потенциальные баги, неиспользуемые переменные и нарушения стиля. Тесты проверяют только динамическую логику и корректность выполнения уже работающего кода. Линтер позволяет отсеять очевидные ошибки ещё до этапа запуска тестов, экономя время и ресурсы.
